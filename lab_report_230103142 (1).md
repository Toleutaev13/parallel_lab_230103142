## 2. Phase 1 — False Sharing & Karp-Flatt Analysis

### Table 1A — Stride sensitivity (p = Pphys = 8)

| Stride (words) | Byte separation | Median (ms) | IQR (ms) | Throughput (Mops/s) |
|---|---|---|---|---|
| 1 | 8 | 1135.472 | 55.284 | 21.1366 |
| 2 | 16 | 1114.835 | 21.760 | 21.5278 |
| 4 | 32 | 1096.441 | 15.771 | 21.8890 |
| 8 | 64 | 1084.824 | 37.435 | 22.1234 |
| 16 | 128 | 1099.492 | 16.896 | 21.8283 |
| 32 | 256 | 1080.074 | 44.611 | 22.2207 |

**Cache-line boundary identification.** No precipitous drop was observed. Going from stride 1 (8 B) to stride 32 (256 B) reduces median time by only 4.9% (1135.5 → 1080.1 ms). The trend is a mild, roughly monotone decrease. The gaps between neighbouring strides (for example stride 8 → 16 is actually +1.4%) are comparable to the IQR, so the step at 64 B (stride = 8, the expected x86-64 line width) is **not statistically distinguishable from noise** in this data. Only a weak hint at 64 B can be claimed. A clear cache-line signature was not reproduced.

### Forensic explanation

- In both series e(p) **grows with p**. The experimentally measured serial fraction is therefore not constant, which means a pure Amdahl serial fraction does not explain the behaviour. Growing e(p) indicates parallel overhead and resource contention that increase with the number of workers.
- The stride = 1 and stride = 16 trajectories are **nearly identical**. At p = 8 the values are 0.2698 vs 0.2549, and at p = 12 they are 0.3155 vs 0.3011. The stride = 1 curve is slightly higher at every p ≥ 2 (a 1–5% relative effect), which is in the direction false sharing would predict but small.
- **Why the effect is small on this CPU.** Each loop iteration is a bytecode-interpreted Python statement, taking about 350 ns per iteration at p = 8 (3×10⁶ iterations per worker in ≈ 1.1 s). A coherence invalidation of a shared line costs on the order of tens to ~100 ns, and it is partly overlapped with interpreter work. The store is a tiny fraction of per-iteration time, so the cache-line ping-pong is largely hidden behind interpreter overhead.
- **Why e(p) rises regardless of stride.** The speedup plateaus at ≈ 2.8 at p = 8 for both strides. This points at a limit that does not depend on cache lines, such as sustained clocks and power/thermal limits of a laptop CPU, shared resources, and the heterogeneous core mix of this processor (see Phase 2). Both strides saturate at the same level, so false sharing cannot be the dominant cause here.
- Conclusion: the experiment confirms the *method* (e(p) rising shows overhead growth) but not a *strong* false-sharing signature on this machine with a pure-Python kernel. The instructor audit item "(a) inflection at 64 B" is therefore only weakly supported by my data.

### Amdahl ceiling comparison

| Quantity | Value |
|---|---|
| Serial fraction s = T_StageA(1)/T₁ | 0.017044 |

| Amdahl predicted S at p = 12 | 10.1054 |

The observed speedup reaches only ≈ 43% of the Amdahl prediction. The serial Stage A (1.7% of T₁) therefore accounts for **only a small part** of the shortfall. Most of the gap comes from other effects: shared memory/cache bandwidth, `Pool` task distribution and result transfer, clock/power scaling under multi-core load, and the loss of per-core performance when workers land on SMT siblings and E-cores. The Amdahl model with a fixed s ignores all of these.

The weak-scaling α rises from 0.017 to 0.086 because Stage A is a fixed-cost serial piece measured against a total time that *also* grows with p, while the non-ideal parallel overhead stretches T_p. Gustafson's S at p = 12 (11.06) looks near-linear, but weak efficiency has fallen to 37%, so the high scaled speedup partly reflects the formula's use of α and not equally good per-worker throughput.

## 5. Phase 4 — Scheduling & Load Imbalance (p = 8, N = 12,000)

| Strategy | Wall time (ms) | λ |
|---|---|---|
| Static block | 7220.64 | 2.2827 |
| Cyclic static | 4734.44 | 1.0292 |
| Dynamic C = 1 | 5100.41 | 1.0327 |
| Dynamic C = 4 | **5059.18** | 1.0294 |
| Dynamic C = 16 | 5180.10 | 1.0389 |
| Dynamic C = 64 | 5224.10 | 1.0608 |
| Dynamic C = 256 | 5438.32 | 1.1232 |
| Dynamic C = 1024 | 6211.52 | 1.5379 |

Per-worker active times (ms), static block: `[31.11, 373.24, 1173.84, 2156.19, 3303.73, 4470.4, 5482.4, 6783.62]`

### Analysis

- **Static block is the worst** (λ = 2.28). Because K(i) grows quadratically with i, worker 0 receives the cheapest range (31 ms) and worker 7 the most expensive (6784 ms). The wall time equals the slowest worker, so seven cores idle at the join barrier.
- **Cyclic static is already near-perfect** (λ = 1.03), because interleaving gives every worker a similar mix of cheap and expensive items. It was in fact the fastest overall (4734 ms), with no synchronisation at all.
- **Dynamic scheduling trade-off.**
  - *C = 1:* the finest grain gives the best balance in principle, but each of the 12,000 claims takes the shared lock and bounces the counter's cache line between cores, adding overhead. Measured: 5100 ms, about 8% slower than cyclic.
  - *C = 4:* a 4× reduction in lock acquisitions keeps balance (λ = 1.029) and gives the best dynamic wall time, **5059 ms**.
  - *C ≥ 64:* synchronisation is cheap but the tail grows. At C = 1024 there are only about 12 chunks for 8 workers. Chunks are claimed in ascending index order, so the **most expensive chunks come last**, and two workers (6041 ms, 6049 ms) end up holding them while others finish at 1349–5526 ms. λ rises to 1.54 and the wall time to 6212 ms.
- **C\* = 4** for this CPU (lowest dynamic wall time; λ is within 0.3% of the best).
- Observation: because the claim order is ascending, a descending (largest-first) order would reduce the large-chunk tail. That was not tested here.

Phase 4 hash used T_wall(Strategy 1) = 7220.64 and T_wall(Strategy 3, C\* = 4) = 5059.18.
